Ted: prioritised product suggestions

Ted has a strong product idea, a clear voice, and good automated safety coverage. The next work should focus on privacy, user separation, delivery reliability, and simpler onboarding before adding more features.

Suggestions only. This document does not claim that any item has been implemented or verified in production.

P0 — before inviting more testers

These items protect users from privacy, safety, or serious reliability failures.

  1. Remove general file access from WhatsApp.WhatsApp users should never be able to read, write, search, or alter unrelated files on the machine running Ted.
  2. Prove two-user separation.Test two accounts at the same time across meals, targets, corrections, reminders, short “done” replies, summaries, and deletion.
  3. Make safety failures stop service.If Ted’s safety checks do not load, Ted should refuse to answer instead of continuing without them.
  4. Move Ted to an always-on machine.A sleeping laptop, closed lid, restart, or logged-out WhatsApp session should not take the product down for every tester.
  5. Make deletion one complete workflow.One confirmed request should clear database records, local chats, media, reminders, queued replies, routing data, and delivery records.
  6. Track each reminder until delivery.Every message needs its own permanent record and a status such as pending, delivered, failed, or abandoned.
  7. Alert outside WhatsApp.Gateway, model, and WhatsApp connection failures need an alert channel that still works when Ted does not.

P1 — next product sprint

These changes improve conversion, trust, and the ability to operate the beta safely.

  1. Shorten compulsory onboarding.Start with name and disclosure/goal. Ask for a check-in time when the person wants a review or reminder.
  2. Let people log immediately.Body and activity details should appear only when somebody requests a calorie target.
  3. Allow calorie setup to be skipped.Meal, water, movement, and commitment coaching should still work without a calorie target.
  4. Measure real activation.Track first useful log and second-day return separately from profile completion.
  5. Create one onboarding contract.The product documents, safety gate, database, and dashboard should describe the same requirements.
  6. Use one calorie-safety rule.Never go below the calculated safety floor and never choose weight loss for the user.
  7. Save calorie calculation evidence.Keep the inputs, maintenance estimate, formula version, chosen target, source, and confirmation time.
  8. Separate normal and administrator access.Routine Ted actions should not use the same secret as cross-user reports and repair tools.
  9. Add traffic limits.Public analytics and administrator endpoints should reject abusive request volumes.
  10. Create a safe preview environment.Every proposed change should be testable before it reaches production.
  11. Add automatic release checks.Tests, lint, type checks, production build, and Hermes patch checks should run for every proposed change.
  12. Record operational events without chat content.Measure processing, delivery, response time, provider failures, and fallback use without copying health messages.
  13. Get legal review before public launch.The privacy notice should clearly cover data, purpose, retention, processors, user rights, complaints, and breach handling.

P2 — performance and product quality

These items improve speed, accuracy, cost, and maintainability after the main risks are closed.

  1. Compress landing-page images.Use responsive WebP or AVIF files instead of placing large photographs directly inside the HTML.
  2. Remove image metadata.Strip phone model, capture time, and other hidden details before publishing images.
  3. Self-host landing-page fonts.A visitor should not need to contact Google to read the page.
  4. Pause off-screen animation.Do not perform animation work for sections the visitor cannot see.
  5. Add browser security rules.Restrict scripts, framing, referrers, file types, and unused browser capabilities.
  6. Make marketing claims exact.Say “a useful estimate” rather than “the same numbers,” and remove automatic workout rescheduling unless it is implemented.
  7. Describe reminders honestly.Say that Ted sends only the reminders and reviews the user chooses.
  8. Use a neutral calorie example.A public 1,400-calorie target can normalise a low target without context.
  9. Stop analytics when its private salt is missing.Do not fall back to a public, guessable value.
  10. Suppress duplicate analytics events.Prevent refreshes and automated traffic from inflating product numbers.
  11. Remove the metrics key from the URL.Use a short-lived secure browser session so the key does not enter history, screenshots, or logs.
  12. Replace full database scans.Store daily totals before the number of events and health records becomes large.
  13. Use smaller processing for routine reminders.Reserve the main model for interpretation, uncertain meals, and personalised coaching.
  14. Split the large safety file carefully.Separate identity, onboarding, nutrition, reminders, delivery, and claims without mixing that refactor with behaviour changes.
  15. Shorten the live personality prompt.Move old incident stories into tests and keep only the current rules in the prompt.
  16. Decide the PDF boundary.Either implement isolated read-only PDF extraction or remove PDF support from the current contract.
  17. Add backups and a restore drill.Protect the local chats and media that are not stored in Convex.
  18. Set log retention.Remove health content from operational logs wherever possible and delete old logs on a fixed schedule.
  19. Test the real browser experience.Check mobile layout, keyboard use, screen readers, reduced motion, and page speed.

P3 — maintenance

These changes reduce future confusion and development cost.

  1. Correct the Hermes patch count.The README should describe the current 13 patches, not 8.
  2. Resolve onboarding documentation conflicts.Remove the competing three-, five-, six-, and eight-requirement descriptions.
  3. Archive old design experiments.Keep the shipped page obvious and mark earlier versions as historical.
  4. Rename the stored user identifier later.`whatsappUserId` contains a protected user key, not a phone number.
  5. Remove unused application code.Review the global Convex browser provider and the production-disabled legacy Hermes route.
  6. Upgrade dependencies in small groups.Keep routine framework updates separate from major TypeScript, ESLint, and Vitest changes.
  7. Upgrade the Vercel command-line tool.Run npm i -g vercel@latest when ready.
  8. Keep progress records current.After each session, record what was implemented, tested, deployed, and still unverified.

Recommended order

File access → two-user separation → fail-closed safety and reliable hosting → deletion → delivery records → simpler onboarding → privacy and release operations → website and cost optimisation.
